# Ask once for task-wide assistance

Use this guide when an assignment needs user input or access decisions. Its purpose is to avoid repeated permission questions while keeping the task's scope clear. It does not grant access by itself or override the host's tool requirements.

## Reuse authorization before asking

Read the user's current and earlier direct instructions. Treat a request to handle a defined task end to end as authorization for ordinary work needed to complete that task within the named environment and any stated limits. Do not ask again for work already authorized. Maintaining these Markdown guides does not require asking for access to a student's VM or collecting student details.

Inspect available task files and tool capabilities first where authorized. Infer routine choices from the assignment, designated template, existing environment, and prior answers. Do not ask the user to choose every command, paragraph, filename, screenshot framing, or dependency when a reasonable task-compliant choice is available.

## Use one setup question only when needed

If task-wide authorization is missing, ask one bundled question, filling in the known target and omitting actions the task does not need:

> Would you like me to handle this task end to end in [selected environment], including working-copy edits, required tool installation, authorized local checks, and screenshot capture with full computer access limited to this task? I will continue on my own within that scope and pause only for missing personal details, credentials or other user-only steps, or actions that need separate approval.

Bundle any genuinely missing target, template, and required personal fields with that setup request. Do not ask separately for installation, opening an application, taking each screenshot, writing each answer, and running each already authorized check. If the user already granted the necessary scope, skip the question entirely.

Record the answer and limits once in the private task record. A yes applies to the actions actually described, the selected environment, and this task; it is not permission for unrelated computer activity or public publication. Respect later changes or revocation.

## Continue after authorization

Perform routine authorized work without additional permission prompts. Follow Installation.MD for missing dependencies, Screenshot.MD for captures, Word.MD for document edits, and Validation.MD for checks. A change from one ordinary task step to the next does not require another setup question.

Use concise progress updates instead of questions about whether to continue. Use current usable screenshot settings and existing template conventions where possible. Keep personal input collection under Input.MD and continue independent work while waiting for any necessary answer.

Ask again only when a material missing fact cannot be inferred, the scope or target materially changes, or a real action requires user participation or separate approval under the host's rules. Examples include credential entry, user-only assignment checkpoints, required legal acceptance, a new external recipient, or an irreversible action outside the agreed scope. Explain the specific reason briefly and ask for only what that step needs. Never click through a host approval or pretend it was granted.

Keep authorization messages in the private task record, not in the technical AI interaction log. Documentation.MD governs what belongs in that log. If access is unavailable, identify the concrete blocker once and progress on independent work rather than repeatedly asking for the same permission.
