# Review and hand off the submission

Use this guide after preparing the working files. It checks readiness to hand the work back to the user. It does not authorize sending the work to an instructor, uploading it to a learning platform, or publishing it to GitHub.

## Check the actual deliverables

Use the register from [Evidence.MD](Evidence.MD), the assignment, and the rubric. Review the files that will actually be delivered, including the copies inside an archive. Do not rely only on an earlier draft or a file list.

1. Confirm the original files remain unchanged and available separately. Preserve hidden content under Formatting.MD. Identify any authorized derivative or conversion limitations.
2. Confirm required answers, user inputs, independent checkpoints, AI disclosures, and prompt records are present and accurate. Check that each checkpoint or question answer has one or two natural sentences, subject to any conflict already resolved with the user.
3. Complete applicable Validation.MD checks. Confirm that actual execution proof exists for every required environment, client, and failure/repair stage. A structural validator pass does not close unrelated requirements.
4. Complete the Evidence.MD consistency and privacy review. Resolve copied explanations, stale status labels, unexplained result mismatches, unreadable screenshots, and exposed secret values in the deliverable copies.
5. Open or render the final document where possible. Check all pages for clipping, missing text, broken tables, misplaced evidence, and remaining placeholders. If visual verification is unavailable, identify it as pending.

Do not remove an assignment's requirements because they were absent from a high-scoring example. A ready status is a review result, not a prediction of a professor's grade.

## Check the package

Verify the required filename, current user's confirmed identifiers, folder structure, and output formats. Flag conflicts between the activity sheet and naming template rather than silently choosing a course code from an older submission.

Create only the requested package in the private working area. Verify its contents and reopen the relevant archived files. Include any required report, completed data, supplied dependencies, prompt log, validation output, screenshots, and process evidence. Do not add unrelated personal files or copies of the workflow repository.

Include local Git history when the assignment requires it. Confirm required branches, commits, integration, and conflict resolution using the available history; do not manufacture a sequence after the fact. Review history for secrets before sharing. If history is not required, do not add it merely because the working folder is a repository.

Check that required evidence corresponds to the delivered file versions. Explain a legitimate earlier milestone snapshot. Repeat affected validation if the substantive tested files changed; do not claim a result for an untested version.

Keep a separate original when preparing an authorized redacted package. Review archive members themselves for private data; hiding a value in the report does not remove it from an image, export, or included history.

When Installation.MD was used, include the relevant environment and dependency information in the requested documentation. Keep virtual-environment directories, installer downloads, package caches, and unrelated setup logs out of the submission unless specifically required; preserve the task's actual dependencies and reproducibility information in the form it requests.

## Choose an accurate handoff status

| Status | Use when | Include in the handoff |
| --- | --- | --- |
| Ready | All applicable required rows are verified, including relevant layout, packaging, and privacy checks | Final file links and a brief statement of the checks performed |
| Partial | Useful work is available, but one or more required rows remain unresolved | Available files, the missing requirements, and exact next actions |
| Blocked | A prerequisite prevents the remaining work from progressing | The blocking input, access, tool, or decision and what is already prepared |

Do not call partial or blocked work ready because the deadline is near or the writing is complete. Continue independent authorized work where possible; a blocker for one step need not stop other useful work.

## Return the work

Lead with the status and provide usable links to the final files. Summarize relevant validation and any material limitations. For unresolved rows, say what remains, why, and who needs to act; do not merely ask the user to finish unspecified work.

Keep the original available separately and distinguish it from the completed or redacted derivative. Leave external submission to the user unless they explicitly request it. Using this public workflow never implies permission to publish the user's completed assignment or private evidence.
